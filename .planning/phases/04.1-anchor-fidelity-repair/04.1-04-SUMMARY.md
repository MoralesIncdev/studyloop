## Safety-predicate evaluation (clause by clause)

D-01 item 3's rule: a token-alias normalization is adoptable only if it (1) relaxes ONLY the id-token subset condition, (2) never touches type equality or the shared-anchor requirement, and (3) collapses no pair in the existing dedup corpus that does not collapse today.

1. **Clause (1), relax id-token only:** technically satisfiable in isolation — a "vent"/"ventilator" alias table could relax condition (c) alone without touching (a) or (b)'s code paths.
2. **Clause (2), never touch type equality:** honored by construction (any token-alias implementation lives inside `tokensOf`, never inside the `k.type !== unit.type` check) — but this is exactly why the fix, even implemented correctly, **cannot resolve F-11's own pair**: condition (a) still blocks it, un-touched by design.
3. **Clause (3), no new false-positive collapses:** not evaluated in depth, because clauses (1)+(2) already establish the fix would not resolve the one finding motivating it, and no other pair in the existing 140-test dedup corpus was found (by RESEARCH, by 04.1-03, or by this plan) that a token-alias relaxation would help.

**Conclusion:** the narrowest-fix bar is not met — not because the fix is unsafe to build, but because it is unnecessary: it would not resolve F-11 (condition (a) blocks independently, and relaxing (a) is explicitly out of scope per the CLUSTER/MECHANISM payload-semantics argument), and no other corpus case needs it. Adding a merge-semantics change to a locked guarantee (D-01) for zero proven benefit fails "prefer the narrowest fix" on the "narrowest" test as much as the "provably safe" one. Disposition: **documented limitation.**

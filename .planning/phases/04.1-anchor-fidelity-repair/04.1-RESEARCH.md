## Summary

This is a root-cause research pass for three MAJOR findings from the 2026-08-10 real-lecture proof run (F-09 rolling-caption duplication, F-10 anchor-timestamp drift up to ~282s on 10/18 units, F-11 a near-duplicate unit escaping dedup). The three findings are related but **not the same bug**, and the evidence gathered here separates them cleanly:

**F-09** (rolling-caption duplication) is a well-known, independently-documented YouTube auto-caption artifact ([yt-dlp#1734](https://github.com/yt-dlp/yt-dlp/issues/1734), [yt-dlp#2956](https://github.com/yt-dlp/yt-dlp/issues/2956), [yt-dlp#6274](https://github.com/yt-dlp/yt-dlp/issues/6274)) — YouTube's auto-caption track emits a "reset" cue (near-zero duration, the tail of the prior line) immediately followed by a "growing" cue (the same text plus a few more words), over and over. `server/src/lib/captionParse.ts`'s `parseCueBlocks` parses every VTT/SRT cue block independently with zero cross-cue awareness, so this raw duplication passes straight through into `captions.json`. This is confirmed against this project's own raw caption data (example below) — it is not a hypothesis.

**F-10** (anchor drift) is the harder and more consequential problem. I read every line of the deterministic merge/dedup pipeline in `server/src/lib/analysis.ts` (`mergeUnitsByFingerprint`, `dedupeNearDuplicateUnits`, `remapEdgeAliases`, `mergeEdgesByFingerprint`, `resolvePearlUnitId`) and `server/src/lib/providers.ts` (the LLM call surface) — **there is no line of StudyLoop code anywhere in this pipeline that computes, offsets, rebases, or otherwise transforms an anchor `t` value.** Every anchor `t` that ends up in `analysis.json` is the model's own per-chunk JSON output, passed through verbatim (union-and-sort by exact `t`, never arithmetic). This means F-10's drift is **not a StudyLoop bug in the traditional sense** — it originates inside the model's own completion. I then cross-referenced every one of this project's 10 drifted units' claimed `t` values against the raw `captions.json` and found: every claimed-but-wrong `t` value is itself a **real segment timestamp from elsewhere in the transcript** — never a fabricated/rounded number — and for the two worst cases (282s and up to 245s drift) it lands suspiciously close to a second, topically-similar restatement of the same fact later in the lecture. This is strong (though not 100%-certain, since it's LLM-internal behavior) evidence that the model is binding the *right quote* to the *wrong nearby timestamp*, most severely when the same fact is taught twice (a teaching pass + a later recap).

**F-11** will very likely **not** resolve automatically once F-10 is fixed, contrary to the original finding's own speculation. I read `dedupeNearDuplicateUnits`'s match predicate directly: it requires (a) identical `unit.type`, (b) at least one shared exact anchor `t`, and (c) one unit's id-token set to be a proper subset of the other's. The specific F-11 pair (`vent-parameters-and-gas-exchange`, type `MECHANISM`) and (`ventilator-parameter-effects-on-gas-exchange`, type `CLUSTER`) fails **both (a) and (c)** independent of anchor time — different types, and `{vent,parameters,and,gas,exchange}` is not a subset of `{ventilator,parameter,effects,on,gas,exchange}` (different tokenization of "vent" vs "ventilator"). Fixing only F-10's timestamps would still leave this pair un-merged.

**Primary recommendation:** Treat this as two independent workstreams with a dependency order, not three. (1) F-09 first: a deterministic, LLM-free rolling-caption reconstruction pass in `captionParse.ts` (or a new module it/`ytdlp.ts` calls) — this also materially improves the ground truth available for (2). (2) F-10: since the bug is in LLM output, not StudyLoop code, the most tractable *code-side* mitigation is a deterministic **post-hoc anchor correction/validation layer** that cross-checks each returned `(t, quote)` pair against the chunk's own known segment list (reusing `anchorVerify.ts`'s existing `buildCaptionIndex`/`matchQuote` machinery, which already does exactly this matching for verification — it is not yet wired in at write-time) — this requires no new LLM calls and is fully unit-testable. A pure prompt-engineering fix (asking the model more insistently to be accurate) is unlikely to be sufficient on its own given the model already violates its own explicit "must fall within this segment's own time range" instruction in 2 of 10 cases. (3) F-11 needs its own, narrower fix to `dedupeNearDuplicateUnits`'s match predicate (or a decision to leave it as a known limitation) — do not assume it disappears for free.

## Root Cause: F-09 — Rolling-caption duplication

**Location: `server/src/lib/captionParse.ts`'s `parseCueBlocks` (used by `parseVttCaptions`, called from `server/src/lib/ytdlp.ts`'s `resolveYoutube`).** [VERIFIED: server/src/lib/captionParse.ts:64-111 — `parseCueBlocks` iterates `blocks` from a naive `\n\s*\n` split and pushes a `CaptionSegment` for every parseable cue independently; there is no lookback at a prior cue's text anywhere in the function]

This is a **documented, external, well-known YouTube auto-caption format quirk**, not a StudyLoop-specific regression — confirmed both by comparison against the clean 2026-08-08 project's `captions.json` (same parser, different video — FINDINGS.md F-09) and by three independent yt-dlp GitHub issues describing the identical symptom: [Fix YouTube's autogenerated subtitles (yt-dlp#1734)](https://github.com/yt-dlp/yt-dlp/issues/1734), [Issue with Youtube auto subtitle (yt-dlp#2956)](https://github.com/yt-dlp/yt-dlp/issues/2956), [Youtube subtitles duplicated (yt-dlp#6274)](https://github.com/yt-dlp/yt-dlp/issues/6274). Per the search summary of these threads: "YouTube's auto-generated VTT files contain duplicate lines because captions are shown progressively with overlapping timestamps" and "the 2-line rolling only occurs in YouTube's auto-generated captions" (not present if a human edits/re-saves captions in YouTube's own editor) — meaning this cannot be avoided by choosing a different yt-dlp output *format* (VTT vs SRT); it is inherent to the underlying auto-caption data yt-dlp reads for this video, and any format yt-dlp emits from it will carry the same rolling structure. [CITED: github.com/yt-dlp/yt-dlp/issues/1734, /2956, /6274 — via WebSearch summary, not independently read in full]

**Concrete shape, read directly from this project's own `captions.json`** [VERIFIED: /Users/antemo/StudyLoopProof-2026-08-10/projects/41b2d9ea-a4b1-428a-b09a-7065ed3dee1f/captions.json, first 10 entries]:

```
2.63  2.64  "Med."
2.64  4.15  "Med. Welcome to another MedCram lecture."
4.15  4.16  "Welcome to another MedCram lecture."
4.16  5.99  "Welcome to another MedCram lecture. We're going to continue in our series"
5.99  6.00  "We're going to continue in our series"
6.00  8.15  "We're going to continue in our series here. We're going to talk about"
8.15  8.16  "here. We're going to talk about"
8.16  9.91  "here. We're going to talk about additional modes of ventilation"
9.91  9.92  "additional modes of ventilation"
9.92 14.39  "additional modes of ventilation specifically now CPAP"
```

The pattern is a strict, mechanically-detectable alternation: a near-zero-duration **"reset" cue** (duration ≈0.01s, text = the tail end of the previous full sentence, i.e. the start of a new rolling window) immediately followed by a **"growing" cue** (same start time, text = the reset cue's text plus a few more words, duration a few seconds) — repeated for the whole transcript. This project has 612 raw segments for a 14:20 (860.54s) video — roughly 2x the segment density a non-rolling caption track would produce for the same speech rate, which independently corroborates the "duplication roughly doubles line count" characterization in FINDINGS.md.

**What a safe reconstruction needs to detect, without corrupting a non-rolling transcript:** the reset/grow pairing is specific to this format — a cue whose text is a **substring/prefix of the immediately-following cue's text**, and/or a cue whose text is **contained within the immediately-preceding cue's text**, both at near-identical or overlapping timestamps. A non-rolling (SRT-style, one-sentence-per-cue) transcript essentially never has this shape (consecutive cues cover disjoint spoken content), so a detector keyed on "cue N+1's text contains cue N's text as a prefix, or cue N's text contains cue N+1's text as a suffix, and their time ranges touch/overlap" should not misfire on clean transcripts — this is the same class of check the 2026-08-08 project's clean `captions.json` (0 rolling artifacts, per F-09's own cross-comparison) would need to pass through untouched to validate the fix doesn't regress the non-rolling case.

## Root Cause: F-10 — Anchor-timestamp drift

### The pipeline performs zero anchor-timestamp arithmetic — verified by reading every merge/dedupe function

I read `server/src/lib/analysis.ts` in full (2028 lines) and `server/src/lib/providers.ts` in full (486 lines). The complete data path for a unit's anchor `t` is:

1. `chunkTranscript` (`analysis.ts:367-396`) builds each chunk's prompt text by joining `[${formatTimestamp(s.start)}] ${s.text}` for every segment in the window — the ABSOLUTE (not chunk-relative) segment start time, taken directly from `captions.json`. [VERIFIED: server/src/lib/analysis.ts:388, quoted verbatim: `` const text = inWindow.map((s) => `[${formatTimestamp(s.start)}] ${s.text}`).join("\n"); ``]
2. `runChunkV3` sends this prompt to the model via `providers.ts`'s `StructuredLLMCaller.call()`, which returns raw `text` from the provider response with zero post-processing of any numeric field. [VERIFIED: server/src/lib/providers.ts:248,298,411 — every provider implementation's `call()` returns `{ kind: "ok", text: ... }` straight from the API response, no numeric transform]
3. `LLMAnalysisClient.runStructured` (`analysis.ts:1008-1029`) `JSON.parse`s that text and validates it against `ChunkV3ResultSchema` via `zod`'s `safeParse` — a structural/type check only (`t: z.number().nonnegative()` [VERIFIED: server/src/lib/analysis.ts:108, quoted verbatim: `` export const UnitAnchorSchema = z.object({ t: z.number().nonnegative(), quote: z.string() }); ``]), never a bounds-vs-chunk-window check.
4. `runAnalysisJobV3`'s loop (`analysis.ts:1947-1971`) pushes `outcome.data.units` straight into `collectedUnits` — no transform.
5. `mergeUnitsByFingerprint` (`analysis.ts:1654-1716`) groups raw units by label fingerprint and, per group, builds `anchorByT` as a `Map<number, string>` keyed by the **exact, unmodified `t`** from each raw anchor (`for (const g of group) for (const a of g.anchors) if (!anchorByT.has(a.t)) anchorByT.set(a.t, a.quote);` [VERIFIED: server/src/lib/analysis.ts:1681-1683]) — this is a union-and-sort, never arithmetic.
6. `dedupeNearDuplicateUnits` (`analysis.ts:1748-1785`) does the same union-by-exact-`t` for its own anchor merge (`analysis.ts:1770-1771`).

**Conclusion: every anchor `t` value that ends up in `analysis.json` is exactly what the model returned for that chunk call.** There is no code location in this repository where F-10 could be introduced by a StudyLoop bug — it is a property of the model's own completion. This reframes the phase's fix surface: prompt engineering and/or a deterministic post-hoc correction layer, not a code arithmetic bug hunt.

F-09's caption duplication plausibly compounds this by roughly doubling the number of near-identical candidate lines the model has to disambiguate between, but the magnitude of drift observed here (40–282s) is far larger than F-09's own reset-cue granularity (~0.01–6s) — **F-09 does not, by itself, explain F-10's magnitude; treat it as a compounding factor, not the root cause.**

### A concrete, code-level, testable gap this phase can close regardless of the deeper "why"

**There is no validation anywhere in the pipeline that checks a returned anchor `t` against its own chunk's `[startSec, endSec]` window, or against the actual position of its own `quote` text.** The chunk prompt states the rule in English ("Every timestamp you output MUST fall within this segment's own time range") but nothing enforces it. This is a concrete, deterministic, unit-testable gap independent of understanding the model's internal failure mode — but it is a **partial** mitigation only: a bounds-check against `[chunk.startSec, chunk.endSec]` would have caught `writing-ac-mode-ventilator-orders`'s and `vent-parameters-and-gas-exchange`'s violations (2 of 10 drifted units, including the single worst case) but **not** the other 8, whose claimed `t` remains inside its own chunk's valid range while still being wrong relative to the quote's true position (including `pressure-support-range`, a DOSAGE safety-tier unit with 160s of drift, entirely within-bounds). A **quote-position cross-check** (does the claimed `t` actually correspond to where `quote` occurs in the chunk's own known segment list?) is a strictly stronger check that would catch all 10 — and the codebase already has the matching primitives for this in `anchorVerify.ts`'s `buildCaptionIndex`/`matchQuote`, just not wired in at analysis-write-time rather than only at read-time verification.

**Important caveat for whichever correction approach the planner chooses: exact substring matching against the *raw* (pre-F-09-fix) caption stream will frequently fail even at a unit's manually-confirmed true position**, because the model's returned `quote` is often a lightly compressed or ASR-typo-corrected paraphrase spanning multiple raw (redundant) caption lines — this is precisely why 31 of the anchor verifier's 32 violations in this run are classified `quote-not-found` (no exact substring anywhere) rather than `time-drift` (exact substring found, just far from `t`) [VERIFIED: docs/proof-evidence-2026-08-10/anchor-verification-report.md — 31/32 violations list `reason: quote-not-found`, only `pressure-support-range` lists `reason: time-drift`]. A robust correction mechanism most likely needs either (a) F-09's dedup fix applied first (fewer, cleaner, longer segments → much higher exact/near-exact match rate), and/or (b) the same normalized (whitespace/case-insensitive) fallback `anchorVerify.ts` already uses for its own "normalized" bucket. **This gives a natural dependency ordering: fixing F-09 first materially de-risks whichever F-10 correction approach the planner picks**, even though the two bugs are architecturally independent.

## Root Cause: F-11 — Near-duplicate escaping dedup

**F-11 will very likely not resolve automatically from an F-10 fix alone — this contradicts the original finding's own "likely resolved as a side effect" speculation, and the contradiction is code-verified, not a guess.**

`dedupeNearDuplicateUnits`'s match predicate (`analysis.ts:1758-1763`) [VERIFIED: server/src/lib/analysis.ts:1758-1763, quoted verbatim:
```
const matchIdx = kept.findIndex((k) => {
  if (k.type !== unit.type) return false;
  if (!k.anchors.some((a) => unitTs.has(a.t))) return false;
  const keptTokens = tokensOf(k.id);
  return isProperSubset(unitTokens, keptTokens) || isProperSubset(keptTokens, unitTokens);
});
```
] requires three conditions simultaneously: (a) identical `unit.type`, (b) at least one **exact** shared anchor `t` (no tolerance window), and (c) one unit's id-token set a proper subset of the other's.

For this run's specific F-11 pair — [VERIFIED: printed directly from analysis.json]
- `vent-parameters-and-gas-exchange`: type `MECHANISM`, id tokens `{vent, parameters, and, gas, exchange}`
- `ventilator-parameter-effects-on-gas-exchange`: type `CLUSTER`, id tokens `{ventilator, parameter, effects, on, gas, exchange}`

**both (a) and (c) fail independent of anchor time:**
- (a) `MECHANISM !== CLUSTER` — the model classified the same underlying fact under two different unit types across its two chunk calls. This is a labeling inconsistency, not caused by F-10.
- (c) `"vent"` and `"ventilator"` are different literal tokens (the fingerprint/subset check does no stemming or fuzzy matching) — `{vent,...}` is not a subset of `{ventilator,...}` in either direction.

Even if F-10's fix made both units' anchor times land close together (satisfying condition (b) exactly, or within a tolerance the planner might add), conditions (a) and (c) would still independently block the merge with the *current* predicate. **The planner should treat F-11 as needing its own explicit decision** — either (i) relax `dedupeNearDuplicateUnits`'s type-equality gate for specific compatible type pairs (e.g. allow `MECHANISM`↔`CLUSTER` when other signals strongly agree), (ii) add a body/summary-text-similarity signal as an alternative match path alongside the token-subset check, or (iii) explicitly accept this as a residual limitation and verify (empirically, after the F-10 fix, via a fresh `verifyAnchors.ts` + a manual near-duplicate scan) whether it recurs on the corrected data before assuming it's fixed.

## Re-run Criteria: what does "anchor verifier re-run yields a clean report" require?

The ROADMAP phrasing is specific: *"anchor verifier re-run **on the 2026-08-10 proof project** yields a clean report"* — the same project, not a fresh lecture. This leaves the planner two structurally different paths, with different cost/certainty tradeoffs:

**Path A — deterministic post-hoc correction (no new LLM spend).** Since F-10's drifted anchors are all groundable to a real position via their own `quote` text (confirmed for all 10 units in `hallucination-audit.md`), and `anchorVerify.ts` already has the exact/normalized matching machinery to locate a quote's true segment, a **write-time correction pass** applied to the *existing* `analysis.json` (using the *existing* — or F-09-fixed — `captions.json`) could, in principle, replace each wrong `t` with the position its own `quote` is actually found at, entirely offline, with zero new zai/glm-5 API calls. This is fast, free, deterministic, and directly testable (`verifyAnchors.ts` can be re-run against the corrected file immediately). It does **not** by itself prove the underlying *pipeline* (a fresh analysis of a *new* lecture) would produce clean anchors — it only proves this one project's stored data can be corrected.

**Path B — live re-analysis (new zai spend, non-deterministic).** Re-running `POST /api/projects/:id/analyze` against this same project (ideally after F-09's caption-dedup fix changes the input `captions.json`) produces a **fresh** LLM completion, which may or may not exhibit the same drift pattern (the exact chunk boundaries are identical since the video is the same, but LLM output is not perfectly deterministic run-to-run). This is the only path that validates the *pipeline itself* got better, not just this one file — but it costs a live API call, is not fully reproducible, and does not guarantee success (if the underlying LLM tendency persists, the re-run could still drift, just differently).

**This document does not decide between them — that is a planning/scope decision** — but flags that the ROADMAP goal's literal wording ("re-run on the 2026-08-10 proof project yields a clean report") is satisfiable by Path A alone if the planner's fix design is "detect and correct drift after the fact" rather than "prevent the LLM from drifting in the first place." If the phase's actual goal is closing PROOF-01's broader claim ("all anchor quotes verbatim-verified... Setup is no longer CONDITIONAL" — i.e. the *mechanism*, not just this file), Path B (or at minimum a second, independent proof lecture exercising the fixed pipeline end-to-end) is very likely necessary to make that broader claim honestly, consistent with how 04-05-SUMMARY.md/PROOF-01's own provenance note treats "supported by evidence" as the bar for flipping a checkbox.

## Common Pitfalls

### Pitfall 1: Fixing F-09 alone and assuming F-10 improves
**What goes wrong:** F-09's caption dedup materially *helps* F-10's correction accuracy (cleaner segments → better quote-position matching), but it does not touch the LLM's own anchor-assignment behavior at all. A team might ship the caption dedup, re-run the proof, and be surprised the anchor drift persists (or even changes shape, since the chunk prompt's line count/spacing will differ post-dedup).
**Why it happens:** F-09 and F-10 are adjacent in the same pipeline and were reported together, inviting the assumption they share a cause. They don't — confirmed by the code read above (zero anchor arithmetic anywhere).
**How to avoid:** Plan and verify F-09 and F-10 as separate deliverables with separate acceptance checks, even if sequenced (F-09 before F-10, per the dependency argued above).
**Warning signs:** A `verifyAnchors.ts` re-run after only the F-09 fix still shows a large `time-drift`/`quote-not-found` count.

### Pitfall 2: A pure bounds-check (`t` within `[chunk.startSec, chunk.endSec]`) treated as "the fix" for F-10
**What goes wrong:** As shown in the empirical table above, 8 of this run's 10 drifted units have a claimed `t` that is *already* inside their own chunk's valid window — a bounds-check alone would silently pass them as "fine" while they remain 40–160s off, including the worst single DOSAGE-tier drift (`pressure-support-range`, 160s, entirely in-bounds).
**Why it happens:** Bounds-checking is the cheapest, most obviously "the prompt already said this" fix to reach for, and it does catch 2 of 10 cases (including the single worst overall drift), which can look like meaningful progress in a quick regression check.
**How to avoid:** Any regression test for this phase must include at least one *in-bounds-but-wrong* fixture (drift within the chunk's own window), not only an out-of-bounds one, or a bounds-check-only fix will pass tests while leaving the majority of the real-world problem unaddressed.
**Warning signs:** A fix's own test suite only exercises out-of-window anchors.

### Pitfall 3: Exact-substring correction against un-deduplicated captions
**What goes wrong:** As shown above, 31/32 of this run's own verifier violations are `quote-not-found` (no exact substring anywhere), not `time-drift` — meaning a correction pass that only tries exact substring matching against the *raw*, F-09-duplicated `captions.json` will fail to relocate most drifted anchors, even ones whose true position is confidently known by manual audit.
**Why it happens:** The model's returned `quote` is frequently a lightly compressed/cleaned paraphrase (ASR-typo-corrected, or spanning what is really 2-3 raw rolling-caption lines), so it was never a literal contiguous substring of the raw duplicated stream to begin with.
**How to avoid:** Sequence F-09's dedup before attempting F-10 correction (per the Re-run Criteria section), and/or use `anchorVerify.ts`'s normalized-match fallback rather than exact-only matching.
**Warning signs:** A correction pass's own success rate (quotes it manages to relocate) is far below the 10/10 rate the manual `hallucination-audit.md` achieved by eye.

## Open Questions

1. **Does the chunk-0-drifts / chunk-1-is-clean pattern replicate on other chunks/lectures, or was it an artifact of this one run?**
   - What we know: In this project's 2-chunk analysis, every drifted unit's true content is exclusively/primarily in chunk 0's window, and every unit exclusively in chunk 1's window anchored correctly.
   - What's unclear: With only 2 data points (2 chunks, 1 video), there's no way to know if this is "the first chunk in a multi-chunk run is systematically less reliable" or simple run-to-run variance between two independent LLM completions.

2. **Does routes/analyze.ts (not read in this session) do anything to `analysis.json` between `runAnalysisJobV3`'s return and the file write that could affect anchors?**
   - What we know: `runAnalysisJobV3`'s own return value is a fully-formed `Analysis` object with `units`/`edges`/`pearls` already merged — no further anchor-affecting step is implied by the function signature.
   - What's unclear: The actual route handler (`routes/analyze.ts`) that calls this function and persists the result was not read in this research session; it's very unlikely to touch anchor values (per `AnalysisSchema`'s own comments about `writeJsonAtomic`), but this should be a 2-minute confirmation at plan time, not an assumption carried into execution.

3. **Is `resolveVideo`'s Innertube caption path (transcriptChain.ts step 3, `lib/innertube.ts`) also susceptible to F-09-style rolling duplication, or is this exclusively a yt-dlp/VTT phenomenon?**
   - What we know: This project's `captions.json` came from the yt-dlp fallback path (`ytdlp.ts`'s `resolveYoutube` → `parseVtt`), not from `transcriptChain.ts`'s lazy Innertube pull (`pullYoutubeTranscript` → `resolveVideo`, which parses `initial_segments` from Innertube's own transcript API response directly, not VTT text — see `server/src/lib/innertube.ts:218-229`, not deeply read in this session).
   - What's unclear: Whether Innertube's `initial_segments` API also exhibits rolling/duplicated cues for auto-generated captions, or whether that's a VTT-specific artifact of yt-dlp's own subtitle extraction.
   - Recommendation: If the planner places the F-09 fix narrowly in `captionParse.ts` (VTT/SRT-specific), it will **not** protect `transcriptChain.ts`'s separate Innertube lazy-pull path (STATE.md's own carried-forward watch item: `pullYoutubeTranscript` has no yt-dlp fallback and is a fully separate code path).

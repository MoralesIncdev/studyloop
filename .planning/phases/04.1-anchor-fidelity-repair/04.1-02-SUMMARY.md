## The two constants (exact, with real-data justification)

**`MIN_OVERLAP_WORDS = 3`** — minimum word length required to strip a PARTIAL overlap match (one that doesn't consume the entire available comparison window). A COMPLETE match — the whole trailing tail-window or the whole incoming cue, whichever is shorter, fully consumed — is always accepted regardless of word count via an escape hatch in `longestSuffixPrefixOverlap` (`len === maxLen`). This resolves a real tension: the smallest genuine overlap observed in the real 2026-08-10 data is exactly 1 word (the transcript's very first reset cue, "Med.", which has no predecessor to compare against beyond itself), so a flat minimum >= 2 would have broken that real case; but a flat minimum of 1 provides zero protection against an accidental word-boundary coincidence (T-04.1-05). Both real fixtures traced by hand confirm every genuine rolling pair — including the 1-word "Med." case — is a COMPLETE match, so raising the partial-match floor to 3 costs nothing against real data while a constructed fixture (`okay cpap is typically the` / `the dog ran home again`, sharing only "the" at the boundary with 4 more words of non-matching content on each side available for comparison) is correctly rejected.

**`TIME_TOUCH_TOLERANCE_SEC = 0.05`** (50ms) — seconds of slack when deciding whether two cues' time ranges "touch or overlap". Every genuine rolling pair in the real 2026-08-10 data touches EXACTLY (one cue's end equals the next cue's start, to the millisecond, in every one of the ten RESEARCH-excerpt cues and all four CPAP-passage cues) — this tolerance exists solely to absorb floating-point rounding from the `ms / 1000` second conversion used when parsing VTT/SRT timestamps or Innertube's `start_ms`/`end_ms` fields, not to bridge a genuine pause between unrelated cues. 50ms is far smaller than any real gap between disjoint sentences (hundreds of ms to seconds) and comfortably larger than any float-rounding error this codebase's second-granularity timestamps could produce.

## Open Question 3 determination (full)

**Question (04.1-RESEARCH.md):** Is `resolveVideo`'s Innertube caption path (`transcriptChain.ts` step 3, `lib/innertube.ts`) also susceptible to F-09-style rolling duplication, or is this exclusively a yt-dlp/VTT phenomenon?

**Determination — CHECKED, UNRESOLVED (not assumed either way):** `innertube.ts`'s `normalizeCaptions` builds segments directly from the transcript/timedtext API's own `initial_segments` node tree (`start_ms`/`end_ms`/`snippet.text` per `TranscriptSegment`-typed node) — this is Innertube's own pre-segmented structure, never VTT/SRT cue TEXT. It is a genuinely different shape than the yt-dlp VTT path this phase's dedup rule was originally designed against, and a static read of `normalizeCaptions` cannot prove whether Innertube's own segment tree carries a reset/grow alternation for a video whose Innertube caption pull actually succeeds. No live rolling Innertube data was ever observed to check against on this machine/network — the proof project's own Innertube caption pull fell through to the yt-dlp fallback twice (`docs/proof-evidence-2026-08-10/FINDINGS.md` F-02), so every real rolling-caption sample available for this phase came from the yt-dlp/VTT path.

**Resolution independent of the open question:** `dedupeRollingCaptions` is applied uniformly on all four `resolveEffectiveTranscript` branches — including step 3, the Innertube path — regardless of how this question eventually resolves, for two reasons that hold either way:
1. It is provably a no-op on non-rolling input (Task 1's own real-fixture deep-equality regression), so applying it where it may not be needed costs nothing.
2. An already-written rolling `captions.json` — exactly what the 2026-08-10 proof project holds — reaches `resolveEffectiveTranscript` through chain step 1's declared-file JSON path, which `transcripts.ts`'s `loadTranscriptFromText` routes to the JSON parser, never through `captionParse.ts`'s cue-block parser Task 1's parse-time dedup lives in. Parse-time dedup alone would leave every existing rolling project stuttering forever, since its `captions.json` is never re-parsed as VTT/SRT text again.

## Ordering relative to `correctTranscriptSegments` (identical on all four branches)

Dedup runs **before** `correctTranscriptSegments` (Phase 2's terms rewrite) on every branch. Terms correction rewrites words (e.g. "metro pro law" → "metoprolol"), which could shift word boundaries; running dedup first means the overlap comparison always sees the exact text YouTube/the ASR adapter actually emitted, not a post-correction rewrite. This is written into the code comment at `transcriptChain.ts`'s step-1 branch and referenced (not re-derived) at steps 2-4.
